\section{Executive summary}

The renovation has moved the project from a Matlab-centered operator workspace toward a standard Python package with an explicit runtime layout, a stable public API, a CLI, and a growing set of Python-native scientific steps.

The most important architectural change is that Matlab is no longer required for routine software use cases such as importing the package, locating data, reading configuration, bootstrapping the runtime tree, validating the expected layout, loading deployment metadata, or importing low-resolution raw ODV files. Matlab is now only needed for the workflow stages that have not yet been ported.

At the time of writing, the following workflow elements are already implemented in Python:

\begin{itemize}[leftmargin=1.5em]
  \item package configuration, runtime path resolution, and data-store bootstrapping;
  \item deployment and tag catalog loading, including JSON fallback and raw ODV-driven discovery;
  \item raw ODV import and profile indexing;
  \item \pkg{lr0} generation via a Python replacement for \pkg{create\_ncargo};
  \item the \pkg{lr0} QC and filtering block;
  \item \pkg{hr0} generation on a regular 1 dbar grid;
  \item the \pkg{hr1} no-TLC branch;
  \item delayed-mode \pkg{apply\_adjustments};
  \item comparison and regression helpers used in tests.
\end{itemize}

The main scientific steps still deferred are the \pkg{fr0/fr1} branch, the thermal-lag pathway, the density-stabilization logic associated with that pathway, and most diagnostic and reporting outputs. A placeholder exists for the historical location-adjustment stage so that the workflow boundary remains explicit.

\section{General description of the toolbox so far}

\subsection{Scientific intent}

MEOP Process assembles and transforms marine mammal CTD observations into Argo-like profile products and derived outputs used for quality control, adjustment, plotting, and public release. The renovated toolbox preserves that mission while reorganizing the software around a Python package structure.

\subsection{Current software intent}

The renovated toolbox now has three simultaneous roles:

\begin{enumerate}[leftmargin=1.6em]
  \item \textbf{Operational wrapper} around the legacy Matlab tasks that are still authoritative.
  \item \textbf{Python-native processing engine} for the workflow parts that have already been ported.
  \item \textbf{Compatibility layer} that keeps the familiar function names from the historical \pkg{python/meop\_process.py} entry point while redirecting behavior through the new package.
\end{enumerate}

\section{What has been done}

\subsection{Repository and packaging}

The codebase has been restructured into a standard \pkg{src/} layout with a package root at \pkg{src/meop\_process/}. A \pkg{pyproject.toml} file now declares the build system, dependencies, and CLI entry point. A compatibility wrapper remains at \pkg{python/meop\_process.py} so the historical invocation style is preserved.

The package now exposes a stable public surface through \pkg{meop\_process.api}. This API keeps the old workflow vocabulary but no longer relies on import-time Matlab startup.

\subsection{Backend separation}

A backend interface now separates Python-owned workflow stages from Matlab-owned ones:

\begin{itemize}[leftmargin=1.5em]
  \item \pkg{runtime/matlab\_backend.py} starts Matlab lazily and only when a Matlab task is actually needed.
  \item \pkg{runtime/python\_backend.py} is the execution target for the growing pure-Python path.
\end{itemize}

This separation is the key enabler for progressive migration.

\subsection{Data layout and runtime ownership}

The package now makes data resolution explicit. Runtime roots such as \pkg{data/tables/}, \pkg{data/catalog/}, \pkg{data/config\_files/}, \pkg{data/raw\_smru\_data\_odv/}, and \pkg{data/raw\_smru\_hr\_data/} are created and validated directly by Python.

This is especially important because some operational datasets are private and not tracked in GitHub. The package now knows where those datasets are expected to live even when the files themselves are absent from the repository.

\subsection{Catalog and metadata discovery}

Deployment and tag resolution is now Python-native. The loader can combine information from:

\begin{itemize}[leftmargin=1.5em]
  \item \pkg{list\_deployment.csv};
  \item \pkg{list\_deployment\_hr.csv};
  \item mirrored JSON metadata such as \pkg{deployment2.json}, \pkg{platform2.json}, \pkg{deployment2\_patch.json}, and \pkg{platform2\_patch.json};
  \item raw ODV profile indexing when catalog rows are incomplete.
\end{itemize}

The \pkg{ct88} example already demonstrates this behavior: the software can recover deployment and platform information from the JSON metadata and the raw ODV files even when the catalog CSV is incomplete.

\subsection{Raw ODV import and \pkg{lr0} creation}

Low-resolution raw files in ODV form are now discovered, mirrored, parsed, and converted in Python. The main result is a Python implementation of the \pkg{create\_ncargo} stage that writes \pkg{*\_lr0\_prof.nc} files.

The current port already covers the core Argo-like structure, platform metadata, timestamps, geolocation, parameters, and profile matrices. The \pkg{ct88-225-12} regression case is used as the reference target.

\subsection{QC/filter block}

The first major scientific filter stage has been ported. The current Python implementation reproduces the historical \pkg{lr0} QC/filter logic closely enough for the \pkg{ct88-225-12} regression case to match the reference file on the key QC arrays and profile counts.

Density-related checks prefer the Python \pkg{gsw} package. In environments where \pkg{gsw} is not available, a fallback remains in place so that the code is still importable and testable, but the intended direction is to rely on \pkg{gsw} as the standard oceanographic engine.

\subsection{High-resolution products and adjustments}

Two further steps are now Python-native:

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{\pkg{hr0}} generation on the regular 1 dbar grid.
  \item \textbf{\pkg{hr1}} generation for the no-TLC branch.
\end{itemize}

In addition, \pkg{apply\_adjustments} is now implemented in Python. It reads runtime coefficient and offset tables, updates adjusted variables and error estimates, and writes those changes back into the available products.

\subsection{Tests and regression harness}

A real automated test suite now exists. The current snapshot passes 29 tests. These tests cover package configuration, data layout, sync helpers, raw import, ODV parsing, \pkg{lr0} generation, QC filtering, \pkg{hr0}, \pkg{hr1} for the no-TLC branch, adjustments, workflow sequencing, and CLI behavior.

The most valuable regression example is the provided \pkg{ct88} case, which includes raw ODV input and a reference \pkg{lr0} NetCDF file. That example now anchors the scientific validation of the Python ports.

A core requirement of the renovation is that the software must know where every class of data belongs, even when those files are not committed to GitHub.

\subsection{Resolution policy}

The package uses explicit resolution rules instead of relying on Matlab working-directory state.

\begin{itemize}[leftmargin=1.5em]
  \item Tables are looked for first in \pkg{data/tables/}, then in the repository root, then in packaged defaults.
  \item Catalogs are looked for first in \pkg{data/catalog/}, then in root-level compatibility copies.
  \item Deployment and platform metadata can be recovered from mirrored JSON files when catalog CSV information is incomplete.
  \item Raw ODV archives are expected in \pkg{input/<deployment>/} and are mirrored into \pkg{data/raw\_smru\_data\_odv/} for actual processing.
\end{itemize}

\subsection{Operational consequence}

This means that private or large datasets do not need to be stored inside the GitHub repository. What must be stable is the runtime contract: the package must know where each dataset is expected to appear, and must expose helpers to bootstrap and validate that contract.

\section{Installation}

\subsection{Python environment}

A minimal editable installation from the repository root is:

\begin{lstlisting}[style=meopcode]
python -m venv .venv
source .venv/bin/activate
pip install -U pip
pip install -e .[dev]
\end{lstlisting}

Current declared core dependencies are:

\begin{itemize}[leftmargin=1.5em]
  \item \pkg{numpy}
  \item \pkg{xarray}
  \item \pkg{h5netcdf}
  \item \pkg{scipy}
  \item \pkg{gsw}
\end{itemize}

\subsection{Matlab dependency}

Matlab is now optional for several tasks. It is only required when the chosen backend must execute legacy workflow steps that have not yet been ported.

In practical terms:

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{No Matlab needed:} package import, config loading, data bootstrap, layout inspection, deployment discovery, raw ODV import, \pkg{lr0}, \pkg{hr0}, \pkg{hr1} for the no-TLC branch, and \pkg{apply\_adjustments}.
  \item \textbf{Matlab still needed:} \pkg{fr0/fr1}, TLC pathway, \pkg{hr2}, calibration plots, LaTeX report generation from the historical Matlab route, and ODV4 export.
\end{itemize}

\subsection{Configuration}

The package can operate with repository-local defaults, but it also supports a machine entry from \pkg{configs.json}. The loader accepts:

\begin{itemize}[leftmargin=1.5em]
  \item an explicit process directory;
  \item an explicit config file;
  \item a machine key;
  \item environment variables such as \pkg{MEOP\_CONFIG\_FILE} and \pkg{MEOP\_MACHINE}.
\end{itemize}

\subsection{Bootstrap and layout validation}

Before the first run, the new utilities can prepare and inspect the runtime tree:

\begin{lstlisting}[style=meopcode]
meop-process --bootstrap-data --show-data-layout
meop-process --validate-data-layout
\end{lstlisting}

These commands create the expected runtime folders, seed packaged CSV tables, and print or validate the full data layout.

\section{Usage}

\subsection{Command-line usage}

The package exposes a console script named \pkg{meop-process}. Example calls are:

\begin{lstlisting}[style=meopcode]
# Import raw ODV data for one deployment
meop-process --deployment ct88 --import_data

# Run the currently available pure-Python path for one tag, no TLC branch
meop-process --smru_name ct88-225-12 --backend python --process_data --notlc

# Apply delayed-mode adjustments to existing products
meop-process --smru_name ct88-225-12 --apply-adjustments
\end{lstlisting}

\subsection{Python API usage}

The stable import surface is \pkg{meop\_process.api}. Example usage:

\begin{lstlisting}[style=meopcode]
from meop_process.api import (
    bootstrap_data_store,
    describe_runtime_data_layout,
    import_raw_data,
    load_info_deployment,
    process_tags,
)
from meop_process.runtime.python_backend import PythonBackend

bootstrap_data_store()
print(describe_runtime_data_layout(as_text=True))

info = load_info_deployment(deployment="ct88")
print(info["raw_profile_count_by_smru"]["ct88-225-12"])

ok = process_tags(
    deployment="ct88",
    smru_name="ct88-225-12",
    notlc=True,
    backend=PythonBackend(),
)
\end{lstlisting}

\subsection{Current processing boundary}

For the main workflow, \pkg{process\_tags()} currently behaves as follows:

\begin{enumerate}[leftmargin=1.6em]
  \item prepare runtime directories and sync mirrored metadata;
  \item load deployment and tag information in Python;
  \item import raw ODV data in Python;
  \item clean previous outputs;
  \item create \pkg{lr0} in Python;
  \item run the location-adjustment placeholder;
  \item create \pkg{hr0} in Python;
  \item run Matlab only if required for remaining unported stages;
  \item patch metadata and apply delayed-mode adjustments in Python;
  \item create \pkg{hr1} in Python for the no-TLC branch, or fall back to Matlab for the TLC branch.
\end{enumerate}

\section{What remains to be done}

\subsection{Deferred scientific processing}

The following core scientific tasks still need work:

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{\pkg{fr0} and \pkg{fr1}.} These remain on Matlab and are intentionally deferred for now.
  \item \textbf{Thermal-lag correction pathway.} This includes the TLC branch itself and the related \pkg{apply\_tlc\_fr} logic.
  \item \textbf{Density-stabilization logic.} The complex Matlab function used in the TLC/high-resolution pathway has not been ported yet.
\end{itemize}

\subsection{Location adjustment}

The historical location-adjustment step is currently represented as a placeholder. This is deliberate: the workflow boundary is preserved, but the implementation is postponed until the surrounding priorities are ready.

\subsection{Diagnostics and analyst support}

A major remaining area is the diagnostic layer used to inspect the data and derive adjustments from historical profiles and climatological references. This work has barely started and will likely require dedicated design.

The likely ingredients are:

\begin{itemize}[leftmargin=1.5em]
  \item Python-native profile diagnostics and section views;
  \item historical reference-data comparison tools;
  \item climatology-based diagnostics;
  \item analyst notebooks or structured reports;
  \item eventually a reproducible workflow to propose and review delayed-mode adjustments.
\end{itemize}

\subsection{Remaining wrappers that still depend on Matlab}

The public functions already exist for \pkg{create\_hr2}, calibration plots, LaTeX report generation, and ODV4 export, but the underlying implementations still delegate to Matlab.

\subsection{Packaging and deployment polish}

A few software-level tasks also remain:

\begin{itemize}[leftmargin=1.5em]
  \item broaden dependency declarations once diagnostics and mapping mature;
  \item add richer documentation around reference datasets and private-data mounting conventions;
  \item create release notes and versioning rules for future public package releases;
  \item decide how much backward compatibility to preserve in filenames, metadata, and CLI behavior.
\end{itemize}

\section{Planned strategy for future developments}

\subsection{Guiding principles}

The next stages should follow these principles:

\begin{enumerate}[leftmargin=1.6em]
  \item Preserve scientific behavior before optimizing implementation details.
  \item Keep the public API stable while internals are migrated.
  \item Prefer small, testable ports over large rewrites.
  \item Use reference cases and comparison harnesses for every scientific transition.
  \item Keep data-location rules explicit and package-owned.
\end{enumerate}

\subsection{Recommended near-term sequence}

\begin{longtable}{>{\raggedright\arraybackslash}p{0.15\textwidth} >{\raggedright\arraybackslash}p{0.75\textwidth}}
\toprule
\textbf{Phase} & \textbf{Recommended scope} \\
\midrule
\endhead
Phase 1 & Consolidate the current Python core, refresh internal documentation, and test with Matlab as soon as a license is available. Confirm parity of \pkg{lr0}, QC, \pkg{hr0}, \pkg{hr1} no-TLC, and \pkg{apply\_adjustments}. \\
Phase 2 & Design the diagnostic layer: data-inspection plots, profile comparisons, and climatology interfaces. This will likely shape the future analyst workflow more than any remaining low-level refactor. \\
Phase 3 & Port \pkg{fr0/fr1} only when the surrounding data model and diagnostics are already stable. \\
Phase 4 & Revisit the TLC and density-stabilization pathway, likely as its own dedicated effort because scientific parity matters more than mechanical translation. \\
Phase 5 & Port or redesign \pkg{hr2}, report generation, calibration plots, and ODV export once the underlying processing chain is settled. \\
\bottomrule
\end{longtable}

\subsection{Recommended diagnostic roadmap}

Because diagnostics will be central for future delayed-mode work, a likely roadmap is:

\begin{enumerate}[leftmargin=1.6em]
  \item create reusable profile-selection and plotting utilities in Python;
  \item build interfaces to historical reference datasets and climatologies;
  \item define a standard comparison bundle for one tag: track map, T/S view, profile overlays, offset estimates, and candidate coefficients;
  \item add regression tests for diagnostic input preparation and summary statistics;
  \item only then decide whether the final analyst interface should be a CLI report, notebook workflow, or a small application.
\end{enumerate}

\section{Recommended immediate next actions}

Given the current state, the most useful immediate actions are:

\begin{itemize}[leftmargin=1.5em]
  \item test the current snapshot against Matlab as soon as the license is available;
  \item verify the Python outputs on a few deployments beyond \pkg{ct88};
  \item document the expected private-data mounting conventions for catalogs, raw data, and references;
  \item start designing the diagnostic layer before reopening the deferred \pkg{fr0} and TLC tasks.
\end{itemize}

\section{Closing note}

The renovation has already crossed the most important software threshold: MEOP Process is no longer locked inside Matlab just to be imported, configured, or pointed at data. The scientific core is not fully migrated yet, but the project now has a clean package skeleton, explicit data contracts, a test suite, and a validated reference case. That creates a much safer foundation for the next development stages.
